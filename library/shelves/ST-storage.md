# ST · 스토리지 내부

> DB 성능 서가의 바닥. 튜닝이 추측이 되지 않게 "디스크에 실제로 무엇이 일어나나"를 본다.

### ST-01 · B-Tree vs LSM-Tree
- 장면: 쓰기가 많은 로그성 데이터를 MySQL에 넣었더니 점점 느려짐 / 누군가 RocksDB·Cassandra를 쓰자고 함.
- 이론: B-Tree는 제자리 갱신(읽기 유리), LSM은 추가 쓰기 + 컴팩션(쓰기 유리). 쓰기 증폭·읽기 증폭·공간 증폭의 맞교환.
- 답해 볼 것: ① LSM이 읽기에서 손해 보는 이유와 블룸 필터 ② 컴팩션이 지연 스파이크를 만드는 방식 ③ 내 워크로드는 어느 쪽인가
- 읽을 곳: DDIA 3장
- 실습: 같은 쓰기 부하를 PostgreSQL vs RocksDB(또는 SQLite vs LevelDB)에 → 처리량·디스크 쓰기량 예측 후 측정
- 손으로: 간단한 LSM(메모리 테이블 + 정렬 파일 + 병합) 100줄
- 끝: 볼트에 3줄

### ST-02 · WAL과 fsync
- 장면: 전원이 나갔다 켜지니 마지막 몇 초 데이터가 없음 / `fsync`를 끄니 갑자기 빨라짐.
- 이론: 먼저 로그에 쓰고 나중에 반영. 커밋 = 로그가 디스크에 닿은 것. `fsync` 비용, 그룹 커밋, `innodb_flush_log_at_trx_commit`·`synchronous_commit`의 뜻.
- 답해 볼 것: ① 커밋 응답 후 전원이 나가도 남는 조건 ② 그룹 커밋이 처리량을 올리는 이유 ③ 설정을 느슨하게 해도 되는 데이터
- 읽을 곳: DDIA 3장 · PostgreSQL 문서 "Write-Ahead Logging"
- 실습: 커밋마다 fsync / 1초마다 / 끔 → 초당 커밋 수 예측 후 측정, 프로세스 강제 종료 후 잃은 건수
- 손으로: 파일에 추가하고 fsync하는 아주 작은 로그
- 끝: 볼트에 3줄

### ST-03 · 페이지와 버퍼 풀
- 장면: 데이터가 메모리보다 커지는 순간 응답이 열 배 느려짐.
- 이론: 페이지(보통 8~16KB) 단위 읽기, 버퍼 풀 적중률, 순차 vs 무작위 I/O, OS 페이지 캐시와의 이중 캐싱.
- 답해 볼 것: ① 행 하나 읽기에 몇 바이트가 디스크에서 오나 ② 적중률 99%와 90%의 차이 ③ 버퍼 풀 크기를 정하는 기준
- 읽을 곳: RealMySQL 4장(아키텍처, 버퍼 풀) · PostgreSQL 문서 "Resource Consumption"
- 실습: 버퍼 풀을 데이터의 50%·100%·200%로 → 무작위 조회 지연 예측 후 측정
- 손으로: 적중률 계산 쿼리
- 끝: 볼트에 3줄

### ST-04 · 디스크와 파일 시스템 감각
- 장면: 클라우드 디스크 IOPS 한도에 걸려 DB 전체가 멈춤.
- 이론: HDD·SSD·네트워크 디스크의 지연 차이, IOPS와 처리량, 큐 깊이, 버스트 크레딧.
- 답해 볼 것: ① SSD 무작위 읽기 지연 대략 ② IOPS 한도에 걸리면 보이는 지표 ③ 로그와 데이터를 다른 디스크에 두는 이유
- 읽을 곳: Jeff Dean "Latency Numbers Every Programmer Should Know" · `fio` 문서
- 실습: `fio`로 순차/무작위, 큐 깊이 1/32 측정 — 숫자를 먼저 예측
- 손으로: 내 서버 디스크 숫자 표
- 끝: 볼트에 3줄
