# TX · 정합성·트랜잭션

> 깊게: [결제 정합성 실험실](../../spring-lab/payment-consistency/README.md) — 아래 카드를 질문 9개로 엮은 것.

### TX-01 · 트랜잭션이 지켜 주는 범위
- 장면: DB 저장은 됐는데 외부 API 호출이 실패. 롤백했다고 생각했는데 외부는 이미 처리됨.
- 이론: ACID는 **한 DB 안**에서만 성립한다. 외부 호출·메시지 발행은 트랜잭션 밖이다. `@Transactional` 안의 HTTP 호출은 롤백되지 않고, 커넥션을 오래 잡는다.
- 답해 볼 것: ① 커밋 전에 외부를 부르면 무엇이 깨지나 ② 커밋 후에 부르면? ③ 트랜잭션 안에서 외부 호출이 3초 걸리면 커넥션 풀은?
- 읽을 곳: DDIA 7장 앞부분 · Spring `@Transactional` 문서(전파·롤백 규칙)
- 실습: 커넥션 풀 10개, 외부 호출 2초를 트랜잭션 안/밖에 두고 동시 50요청 → 대기 시간 예측 후 측정
- 손으로: 외부 호출을 트랜잭션 밖으로 빼는 서비스 메서드 구조
- 끝: 볼트에 3줄

### TX-02 · 격리 수준과 이상 현상
- 장면: 잔액 확인 후 차감했는데 마이너스가 됨 / 같은 쿼리를 두 번 했는데 결과가 다름.
- 이론: dirty read · non-repeatable read · phantom · **lost update** · **write skew**. READ COMMITTED vs REPEATABLE READ(MySQL은 갭 락, PostgreSQL은 스냅샷 + 직렬화 실패). 격리 수준이 막는 것과 못 막는 것.
- 답해 볼 것: ① lost update는 REPEATABLE READ에서 막히나 (MySQL vs PostgreSQL) ② write skew 예 하나 ③ SERIALIZABLE의 비용은 어디서 나오나
- 읽을 곳: DDIA 7장 "약한 격리 수준" · PostgreSQL 문서 "Transaction Isolation" · RealMySQL 5장
- 실습: 두 세션을 손으로 열고 이상 현상 5개를 격리 수준별로 재현 (표: 예측 vs 실제)
- 손으로: 조건부 `UPDATE ... WHERE balance >= ?` 와 `SELECT ... FOR UPDATE` 두 방식
- 끝: 볼트에 3줄

### TX-03 · 멱등성
- 장면: 사용자가 결제 버튼을 두 번 누름 / 클라이언트 재시도로 주문이 두 개.
- 이론: 같은 요청은 몇 번 와도 결과가 한 번. 멱등 키 + 유니크 제약 + 저장된 응답 재생 + "처리 중" 상태. 자연 멱등(PUT)과 만든 멱등(POST + 키).
- 답해 볼 것: ① 첫 요청이 처리 중일 때 두 번째가 오면 ② 키 보관 기간은 ③ 요청 본문이 다른데 키가 같으면
- 읽을 곳: Stripe 블로그 "Designing robust and predictable APIs with idempotency" · brandur.org "Implementing Stripe-like Idempotency Keys in Postgres"
- 실습: 같은 키로 동시 100요청 → 돈이 몇 번 움직일지 예측 후 측정
- 손으로: 멱등 키 테이블 DDL과 처리 흐름
- 끝: 볼트에 3줄

### TX-04 · 타임아웃은 실패가 아니라 "모름"
- 장면: PG 응답 타임아웃 → 실패 처리 → 다음 날 정산에 승인 건이 있음.
- 이론: 네트워크 너머의 결과는 세 가지(성공·실패·모름). 모름은 조회·확정 잡·대사로 닫는다. exactly-once는 전달이 아니라 처리의 멱등으로 흉내 낸다.
- 답해 볼 것: ① 타임아웃 뒤 재시도해도 되는 조건 ② "모름" 상태를 누가 언제 닫나 ③ exactly-once가 불가능한 이유 한 문장
- 읽을 곳: DDIA 8장 "신뢰성 없는 네트워크" · 9장 앞부분
- 실습: 가짜 PG가 처리 후 응답을 버리게 하고 내부·외부 상태 차이를 센다
- 손으로: 상태 `UNKNOWN` → 확정 잡의 판단 로직
- 끝: 볼트에 3줄

### TX-05 · 트랜잭셔널 아웃박스
- 장면: 주문은 저장됐는데 "주문 완료" 이벤트가 안 나감 / 두 번 나감.
- 이론: 비즈니스 변경과 이벤트를 **같은 DB 트랜잭션**에 쓰고, 릴레이가 나중에 발행한다. at-least-once → 소비자 멱등 필수. 폴링 vs CDC(Debezium).
- 답해 볼 것: ① 릴레이가 발행 후 표시 전에 죽으면 ② 순서가 중요할 때 ③ 아웃박스 테이블은 언제 지우나
- 읽을 곳: microservices.io "Transactional outbox" · DDIA 11장 "변경 데이터 캡처"
- 실습: 릴레이를 무작위로 죽였다 살리며 유실 0 / 중복 수 측정
- 손으로: 릴레이 한 번 도는 쿼리 (`FOR UPDATE SKIP LOCKED`)
- 끝: 볼트에 3줄

### TX-06 · 사가와 보상
- 장면: 주문 → 결제 → 재고 차감 중 재고에서 실패. 결제는 이미 됨.
- 이론: 분산 트랜잭션(2PC) 대신 단계별 로컬 트랜잭션 + 실패 시 보상. 오케스트레이션 vs 코레오그래피. 보상은 "되돌리기"가 아니라 "새 거래"(환불).
- 답해 볼 것: ① 보상도 실패하면 ② 사가 중간 상태가 사용자에게 보이면 ③ 2PC를 피하는 이유
- 읽을 곳: microservices.io "Saga" · DDIA 9장 "분산 트랜잭션"
- 실습: 3단계 사가에서 2단계 실패를 주입하고 최종 상태 표를 예측·확인
- 손으로: 오케스트레이터의 상태 전이 표
- 끝: 볼트에 3줄
