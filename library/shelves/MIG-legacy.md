# MIG · 레거시·마이그레이션

### MIG-01 · 스트랭글러 패턴
- 장면: 오래된 시스템을 한 번에 갈아엎자는 계획이 1년째 미완성.
- 이론: 앞단에서 경로를 나눠 기능 하나씩 새 시스템으로, 옛 시스템은 점점 줄어든다. 되돌릴 수 있는 단계.
- 답해 볼 것: ① 처음 옮길 기능 고르는 기준 ② 두 시스템이 같은 데이터를 쓰면 ③ 끝났다는 기준
- 읽을 곳: Martin Fowler "StranglerFigApplication"
- 실습: 프록시 뒤에 옛 앱·새 앱을 두고 경로 하나씩 옮기며 오류율 측정
- 손으로: 경로 전환 표
- 끝: 볼트에 3줄

### MIG-02 · 데이터 이전과 검증
- 장면: 이전은 끝났는데 몇 달 뒤 일부 데이터가 빠진 걸 발견.
- 이론: 전체 복사 + 변경분 따라잡기(CDC), 검증(건수·합계·체크섬·표본 비교), 이전 중 쓰기 처리, 되돌리기 계획.
- 답해 볼 것: ① 건수만 맞추면 놓치는 것 ② 이전 중 들어온 쓰기 ③ 컷오버 순간의 순서
- 읽을 곳: Stripe 블로그 "Online migrations at scale"
- 실습: 테이블 하나를 새 스키마로 옮기며 쓰기를 계속 넣고, 검증 쿼리로 차이 0 만들기
- 손으로: 검증 쿼리 묶음
- 끝: 볼트에 3줄

### MIG-03 · 이중 쓰기·그림자 읽기
- 장면: 새 시스템을 믿고 바꿨더니 결과가 미묘하게 다름.
- 이론: 옛것과 새것에 같이 쓰기, 새것에서 그림자로 읽어 비교만, 차이율이 0에 가까워지면 전환.
- 답해 볼 것: ① 이중 쓰기가 실패하면(TX 서가와 연결) ② 비교할 때 무시할 차이 ③ 전환 기준 숫자
- 읽을 곳: GitHub Engineering "Scientist"(그림자 실행 라이브러리)
- 실습: 옛 계산 vs 새 계산을 같은 입력으로 돌려 차이 리포트
- 손으로: 비교 로거
- 끝: 볼트에 3줄

### MIG-04 · 레거시 코드 다루기
- 장면: 테스트 없는 코드를 고쳐야 함.
- 이론: 특성 테스트(지금 동작을 고정), 이음새(seam), 작은 리팩터링, 고치기 전에 이해한 것을 글로.
- 답해 볼 것: ① 특성 테스트가 지키는 것 ② 이음새를 만드는 가장 작은 변경 ③ 리팩터링과 기능 변경을 섞지 않는 이유
- 읽을 곳: Michael Feathers 『레거시 코드 활용 전략』 · Martin Fowler 『리팩터링』
- 실습: 테스트 없는 코드에 특성 테스트를 붙이고 리팩터링 한 단계
- 손으로: 특성 테스트
- 끝: 볼트에 3줄
