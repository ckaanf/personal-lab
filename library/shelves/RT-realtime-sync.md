# RT · 실시간 상태 동기화

> 버튜버 무대의 "인터랙션"은 게임 서버와 같은 문제다 — 여러 사람이 보는 하나의 상태를 지연 속에서 맞춘다.

### RT-01 · 권위 서버와 틱
- 장면: 시청자 반응(박수·투표)이 사람마다 다른 순서로 보임.
- 이론: 서버가 진짜 상태를 갖고(권위), 정해진 간격(틱)으로 입력을 모아 계산해 내려보낸다. 틱 속도와 대역폭·CPU의 맞교환.
- 답해 볼 것: ① 클라이언트가 상태를 정하면 생기는 일 ② 틱 20Hz vs 60Hz ③ 늦게 온 입력은 어느 틱에
- 읽을 곳: Gabriel Gambetta "Fast-Paced Multiplayer"(웹 연재) 1편
- 실습: WebSocket 권위 서버로 공유 카운터 → 틱 속도별 대역폭·지연 예측 후 측정
- 손으로: 틱 루프
- 끝: 볼트에 3줄

### RT-02 · 스냅샷과 델타
- 장면: 상태 전체를 매번 보내니 대역폭이 감당이 안 됨.
- 이론: 전체 스냅샷 vs 바뀐 것만(델타), 마지막으로 받은 걸 기준으로 델타, 손실 시 전체 다시, 직렬화 형식(JSON vs 바이너리).
- 답해 볼 것: ① 델타의 기준을 누가 아나 ② 패킷 하나가 빠지면 ③ JSON vs 바이너리 크기 차이
- 읽을 곳: Glenn Fiedler "Gaffer On Games — Snapshot Compression"
- 실습: 같은 상태 흐름을 전체/델타, JSON/바이너리로 → 초당 바이트 예측 후 측정
- 손으로: 델타 계산
- 끝: 볼트에 3줄

### RT-03 · 예측과 보정, 보간
- 장면: 내 입력이 서버 왕복만큼 늦게 반영돼 답답함 / 다른 사람 움직임이 뚝뚝 끊김.
- 이론: 클라이언트 예측(먼저 보여 주기) + 서버 결과로 보정, 다른 객체는 약간 과거를 보간해서 보여 주기.
- 답해 볼 것: ① 예측이 틀렸을 때 사용자에게 보이는 것 ② 보간 지연을 얼마로 ③ 버튜버 모션에는 어느 쪽이 맞나
- 읽을 곳: Gambetta 연재 2~3편
- 실습: 지연 100·300ms에서 예측 없음/있음 체감을 영상으로 비교
- 손으로: 보간 함수
- 끝: 볼트에 3줄

### RT-04 · 방(룸)과 확장
- 장면: 한 방에 1천 명이 들어오자 서버 하나가 감당 못 함.
- 이론: 방 단위 샤딩, 방 위치 찾기(라우팅), 같은 방 서버 간 메시지(pub/sub), 관전자와 참여자 분리.
- 답해 볼 것: ① 방을 서버에 배정하는 법 ② 서버가 죽으면 방 상태는 ③ 참여자 10명 + 관전자 1만 명 구조
- 읽을 곳: FO 서가 · Discord Engineering "How Discord Scaled Elixir to 5,000,000 Concurrent Users"
- 실습: 방 여러 개를 서버 2대에 나누고 서버 하나를 죽여 복구 시간 측정
- 손으로: 방 배정 규칙
- 끝: 볼트에 3줄
