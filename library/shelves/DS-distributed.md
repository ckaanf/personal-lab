# DS · 분산 시스템 기초

### DS-01 · 타임아웃 정하기
- 장면: 하위 서비스가 느려지자 우리 서비스 스레드가 전부 대기.
- 이론: 연결 타임아웃과 읽기 타임아웃은 다르다. 타임아웃은 하위의 p99와 상위의 예산에서 나온다. 타임아웃 없는 호출은 언젠가 전체를 멈춘다.
- 답해 볼 것: ① 상위 예산 1초, 하위 호출 3번이면 각 타임아웃은 ② 연결 타임아웃이 필요한 상황 ③ 타임아웃 기본값이 무한인 클라이언트
- 읽을 곳: DDIA 8장 · AWS Builders' Library "Timeouts, retries, and backoff with jitter"
- 실습: 하위 지연을 0.1→5초로 올리며 우리 쪽 처리량 예측 후 측정 (타임아웃 있음/없음)
- 손으로: 호출별 타임아웃 예산 표
- 끝: 볼트에 3줄

### DS-02 · 재시도와 백오프
- 장면: 하위가 잠깐 죽었다 살아났는데, 재시도 폭주로 다시 죽음.
- 이론: 재시도는 멱등한 요청만. 지수 백오프 + 지터, 재시도 예산, 여러 층에서 재시도하면 곱해진다.
- 답해 볼 것: ① 3층 × 3회 재시도면 최대 몇 배 ② 지터가 없으면 ③ 재시도하면 안 되는 오류
- 읽을 곳: AWS Builders' Library (위 글) · Marc Brooker "Exponential Backoff And Jitter"
- 실습: 하위 10초 장애 → 재시도 정책별 하위 부하 그래프 예측 후 측정
- 손으로: 백오프 + 지터 계산 함수
- 끝: 볼트에 3줄

### DS-03 · 서킷 브레이커와 벌크헤드
- 장면: 결제 PG 하나가 느려져 주문 API 전체가 느려짐.
- 이론: 실패가 이어지면 빨리 실패하고(열림), 가끔 확인(반열림). 벌크헤드로 자원을 나눠 한 하위의 장애가 번지지 않게.
- 답해 볼 것: ① 열림 기준(실패율 vs 느린 호출 비율) ② 반열림에서 몇 개를 보내나 ③ 서킷이 열렸을 때 사용자에게 줄 것
- 읽을 곳: Resilience4j 문서 · Michael Nygard 『Release It!』 5장(안정성 패턴)
- 실습: 하위 지연 주입 → 서킷 없음/있음에서 우리 p99 비교
- 손으로: 대체 응답(fallback) 하나
- 끝: 볼트에 3줄

### DS-04 · 시계와 순서
- 장면: 두 서버 로그의 시간이 뒤바뀌어 원인 분석 실패 / `updated_at`으로 최신을 정했다가 덮어씀.
- 이론: 서버 시계는 어긋난다(NTP). 순서가 필요하면 시계 대신 버전·시퀀스. last-write-wins의 위험.
- 답해 볼 것: ① 벽시계 vs 단조 시계 ② LWW가 데이터를 잃는 예 ③ 순서를 보장받는 방법 두 개
- 읽을 곳: DDIA 8장 "신뢰성 없는 시계"
- 실습: 시계를 일부러 어긋나게 한 두 컨테이너에서 LWW로 덮어쓰기 재현
- 손으로: 버전 비교 업데이트
- 끝: 볼트에 3줄

### DS-05 · 복제 지연과 일관성
- 장면: 글을 쓰고 새로고침했는데 안 보임(읽기 복제본).
- 이론: 비동기 복제의 지연, read-your-writes, 단조 읽기, 쓰기 직후 주 DB에서 읽기.
- 답해 볼 것: ① read-your-writes를 보장하는 방법 ② 복제 지연을 재는 지표 ③ 강한 일관성이 필요한 화면
- 읽을 곳: DDIA 5장
- 실습: 복제본에 지연을 넣고 "쓰고 바로 읽기" 실패율 측정 → 라우팅 규칙으로 고치기
- 손으로: 쓰기 후 N초는 주 DB로 보내는 규칙
- 끝: 볼트에 3줄
