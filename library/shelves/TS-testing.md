# TS · 테스트 전략

### TS-01 · 무엇을 테스트하나 (피라미드와 경계)
- 장면: 테스트는 많은데 장애는 못 막음 / 리팩터링하면 테스트가 다 깨짐.
- 이론: 동작을 테스트하고 구현은 테스트하지 않는다. 단위·통합·끝단의 비율, 목(mock)이 많을수록 거짓 안심.
- 답해 볼 것: ① 리팩터링에 깨지는 테스트의 공통점 ② 목 대신 진짜를 쓸 곳 ③ 지난 장애를 막았을 테스트
- 읽을 곳: Martin Fowler "The Practical Test Pyramid" · Google Testing Blog "Test Sizes"
- 실습: 지난 버그 하나를 재현하는 테스트를 먼저 쓰고(빨강) 고치기
- 손으로: 그 테스트
- 끝: 볼트에 3줄

### TS-02 · 진짜 DB로 테스트 (Testcontainers)
- 장면: H2에서는 통과, 운영 MySQL에서는 실패.
- 이론: 같은 엔진으로 테스트, 컨테이너 재사용으로 속도, 데이터 격리(트랜잭션 롤백 vs 정리).
- 답해 볼 것: ① H2가 숨기는 차이 3개 ② 테스트 간 데이터 격리 방법 ③ 느린 통합 테스트를 빠르게
- 읽을 곳: Testcontainers 문서 "Getting started" · Spring Boot "Testcontainers support"
- 실습: H2 vs 실제 엔진에서 다르게 동작하는 쿼리 찾기
- 손으로: 공용 컨테이너 테스트 기반 클래스
- 끝: 볼트에 3줄

### TS-03 · 동시성·불변식 테스트
- 장면: 단위 테스트는 다 통과하는데 동시에 쓰면 깨짐.
- 이론: 래치로 동시 시작, 반복 실행, 불변식(합계·유일성)으로 채점, 속성 기반 테스트.
- 답해 볼 것: ① 동시 테스트가 가끔만 실패할 때 ② 불변식 예 3개 ③ 속성 기반 테스트가 찾는 버그
- 읽을 곳: jqwik 문서
- 실습: TX·CC 서가의 버그 하나를 동시성 테스트로 잡기
- 손으로: 동시 실행 테스트 유틸
- 끝: 볼트에 3줄

### TS-04 · 계약 테스트
- 장면: 다른 팀이 API를 바꿔 우리 서비스가 배포 후에 터짐.
- 이론: 소비자 주도 계약, 제공자 검증, 스텁 공유. 끝단 테스트 대신 경계에서 막기.
- 답해 볼 것: ① 계약 테스트가 막는 것과 못 막는 것 ② 계약은 누가 소유하나 ③ 이벤트(메시지)에도 쓰는 법
- 읽을 곳: Pact 문서 "Introduction"
- 실습: 제공자 필드 변경 → 계약 테스트가 배포 전에 잡는지 확인
- 손으로: 계약 하나
- 끝: 볼트에 3줄
