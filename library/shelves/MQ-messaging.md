# MQ · 메시징·이벤트

### MQ-01 · 전달 보장
- 장면: 컨슈머 재시작 후 메시지가 두 번 처리됨 / 한 건이 사라짐.
- 이론: at-most-once / at-least-once / "effectively once". 오프셋 커밋 시점이 보장을 정한다. 결국 소비자 멱등.
- 답해 볼 것: ① 처리 전에 커밋하면 ② 처리 후에 커밋하면 ③ Kafka "exactly-once"가 실제로 보장하는 범위
- 읽을 곳: Kafka 문서 "Message Delivery Semantics" · DDIA 11장
- 실습: 처리 중 컨슈머를 죽이고 커밋 시점별 유실·중복 수 예측 후 측정
- 손으로: 처리 기록 테이블로 만든 멱등 소비자
- 끝: 볼트에 3줄

### MQ-02 · 파티션과 순서
- 장면: 같은 주문의 "생성"보다 "취소"가 먼저 처리됨.
- 이론: 순서는 파티션 안에서만. 키 선택이 순서와 쏠림을 정한다. 파티션 수 변경 시 키 재분배.
- 답해 볼 것: ① 순서가 필요한 단위는 ② 핫 키가 생기면 ③ 컨슈머 수 > 파티션 수면
- 읽을 곳: Kafka 문서 "Design" · 『카프카 핵심 가이드』 4장(컨슈머)
- 실습: 키 없음/있음으로 같은 주문 이벤트 순서 뒤집힘 비율 측정
- 손으로: 키 설계 메모 (무엇을 키로, 왜)
- 끝: 볼트에 3줄

### MQ-03 · 리밸런싱과 컨슈머 랙
- 장면: 배포할 때마다 처리가 몇 분 멈춤 / 랙이 계속 늘어남.
- 이론: 컨슈머 그룹 리밸런싱, `max.poll.interval.ms`, 느린 처리로 그룹에서 쫓겨남, 협력적 리밸런싱.
- 답해 볼 것: ① 처리가 poll 간격보다 길면 ② 랙을 보는 지표 ③ 배포 중 리밸런싱을 줄이는 법
- 읽을 곳: Kafka 문서 "Consumer Configs"
- 실습: 처리 시간을 늘려 리밸런싱 유발 → 중복·멈춤 시간 측정
- 손으로: 랙 경보 기준 정하기
- 끝: 볼트에 3줄

### MQ-04 · 실패 메시지와 DLQ
- 장면: 형식이 깨진 메시지 하나 때문에 파티션 전체가 멈춤(poison pill).
- 이론: 재시도 토픽, DLQ, 재처리 도구, 원인 보존(헤더에 오류).
- 답해 볼 것: ① 무한 재시도의 결과 ② DLQ에 넣을 오류 vs 재시도할 오류 ③ DLQ를 누가 언제 비우나
- 읽을 곳: Spring Kafka 문서 "Non-Blocking Retries"
- 실습: 깨진 메시지 주입 → 정책별 처리 멈춤 시간
- 손으로: 오류 분류 표
- 끝: 볼트에 3줄

### MQ-05 · 이벤트 설계와 스키마 진화
- 장면: 프로듀서가 필드를 바꿨더니 다른 팀 컨슈머가 터짐.
- 이론: 이벤트 = 일어난 사실(과거형). 알림 이벤트 vs 상태 전달 이벤트. 하위 호환(필드 추가는 OK, 삭제·의미 변경은 X), 스키마 레지스트리.
- 답해 볼 것: ① 이벤트에 전체 상태를 담을지 ② 필드 이름을 바꾸려면 ③ 버전 필드의 쓸모
- 읽을 곳: DDIA 4장(부호화와 발전)
- 실습: 옛 컨슈머/새 프로듀서 조합 4가지 호환 표 예측 후 확인
- 손으로: 이벤트 하나의 스키마와 변경 규칙
- 끝: 볼트에 3줄
