# API · API 설계·호환성

### API-01 · 하위 호환과 버전
- 장면: 응답 필드 하나 바꿨는데 앱 구버전이 터짐.
- 이론: 추가는 안전, 삭제·의미 변경은 깨짐. 관대한 읽기(모르는 필드 무시). 버전은 URL·헤더·필드 중 어디에. 폐기 일정.
- 답해 볼 것: ① enum 값 추가가 깨는 경우 ② null 의미 바꾸기 ③ 버전을 올리지 않고 바꾸는 법
- 읽을 곳: Google API Design Guide "Compatibility"
- 실습: 옛 클라이언트 테스트를 고정해 두고 변경 5가지가 깨는지 예측 후 확인
- 손으로: 호환 규칙 체크리스트
- 끝: 볼트에 3줄

### API-02 · 오류 응답 설계
- 장면: 클라이언트가 오류 문구를 파싱해서 분기함.
- 이론: HTTP 상태 + 기계가 읽는 오류 코드 + 사람용 메시지, 재시도 가능 여부, RFC 9457(Problem Details).
- 답해 볼 것: ① 400과 422 ② 재시도 가능 여부를 알리는 법 ③ 내부 예외가 새지 않게
- 읽을 곳: RFC 9457
- 실습: 지금 API 오류 응답 10개를 모아 분류표 만들기
- 손으로: 오류 응답 형식과 전역 핸들러
- 끝: 볼트에 3줄

### API-03 · 페이지네이션·필터·정렬
- 장면: 목록 API가 페이지마다 중복·누락(실시간으로 데이터가 바뀜).
- 이론: 오프셋 vs 커서, 안정적 정렬 키, 다음 커서 불투명 처리, 총개수의 비용.
- 답해 볼 것: ① 데이터가 추가될 때 오프셋 결과 ② 커서에 무엇을 담나 ③ 총개수를 꼭 줘야 하나
- 읽을 곳: DB-06 카드 · Slack Engineering "Evolving API Pagination at Slack"
- 실습: 조회 중 데이터 추가 → 오프셋/커서별 중복·누락 수
- 손으로: 커서 인코딩·디코딩
- 끝: 볼트에 3줄

### API-04 · 속도 제한
- 장면: 한 고객의 배치가 API 전체를 느리게 함.
- 이론: 토큰 버킷, 슬라이딩 윈도, 고객별·엔드포인트별, 분산 환경에서 카운트, 429 + Retry-After.
- 답해 볼 것: ① 토큰 버킷이 순간 폭주를 허용하는 방식 ② 서버 여러 대에서 세기 ③ 제한에 걸린 클라이언트가 할 일
- 읽을 곳: Stripe 블로그 "Scaling your API with rate limiters"
- 실습: Redis 토큰 버킷 → 폭주 패턴별 허용·거절 수 예측 후 측정
- 손으로: 토큰 버킷 (Lua 또는 Java)
- 끝: 볼트에 3줄
