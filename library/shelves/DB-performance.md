### DB-01 · 실행 계획 읽기
- 장면: 어제까지 빠르던 쿼리가 데이터가 늘자 10초.
- 이론: 옵티마이저는 통계로 비용을 추정한다. `EXPLAIN`은 추정, `EXPLAIN ANALYZE`는 실제. 읽는 순서(안쪽부터), rows 추정 vs 실제의 차이가 문제의 신호.
- 답해 볼 것: ① type=ALL / Seq Scan이 오히려 나은 경우 ② 추정 rows가 크게 틀리는 이유 ③ ANALYZE를 운영에서 조심할 점
- 읽을 곳: PostgreSQL 문서 "Using EXPLAIN" · RealMySQL 10장(실행 계획)
- 실습: 100만 행에서 같은 쿼리를 인덱스 전/후로 — 실행 시간과 읽은 행 수를 먼저 예측
- 손으로: 실행 계획 한 장을 줄마다 해석한 메모
- 끝: 볼트에 3줄

### DB-02 · 인덱스 설계
- 장면: 인덱스를 걸었는데 안 탐 / 인덱스가 많아져 쓰기가 느림.
- 이론: B-Tree, 복합 인덱스의 왼쪽 접두사, 선택도, 커버링 인덱스, 정렬·범위 조건 뒤 컬럼은 못 씀. 인덱스는 쓰기 비용.
- 답해 볼 것: ① (a,b,c) 인덱스로 `WHERE b=? ORDER BY c`는? ② 카디널리티 낮은 컬럼을 앞에 두면 ③ 커버링이 빠른 이유
- 읽을 곳: RealMySQL 8장(인덱스) · "Use The Index, Luke"(use-the-index-luke.com)
- 실습: 같은 조회에 인덱스 4가지 → 읽은 페이지 수·시간 예측 후 측정, INSERT 처리량 변화도
- 손으로: 실제 화면의 조회 3개를 보고 인덱스 설계
- 끝: 볼트에 3줄

### DB-03 · 락과 데드락
- 장면: 배치와 API가 동시에 돌면 가끔 데드락 / 락 대기 타임아웃.
- 이론: 행 락, 갭·넥스트키 락(MySQL), 락 순서, 데드락 감지와 희생자, 락 대기 vs 데드락의 차이.
- 답해 볼 것: ① 두 트랜잭션이 서로 다른 순서로 두 행을 잡으면 ② 인덱스가 없을 때 UPDATE가 잡는 락 범위 ③ 데드락 로그에서 볼 것
- 읽을 곳: RealMySQL 5장 · PostgreSQL 문서 "Explicit Locking"
- 실습: 데드락을 일부러 만들고 로그 읽기 → 락 순서 고정으로 없애기
- 손으로: 락 순서를 고정하는 코드
- 끝: 볼트에 3줄

### DB-04 · MVCC와 긴 트랜잭션
- 장면: 아무것도 안 하는 트랜잭션 하나 때문에 DB가 점점 느려짐 / PostgreSQL 테이블이 계속 커짐.
- 이론: MVCC는 옛 버전을 남긴다. 긴 트랜잭션은 정리(언두 퍼지 / VACUUM)를 막는다. bloat.
- 답해 볼 것: ① 열어 둔 트랜잭션이 다른 세션에 주는 영향 ② VACUUM과 autovacuum ③ 히스토리 리스트 길이(MySQL)
- 읽을 곳: DDIA 7장 "스냅샷 격리" · PostgreSQL 문서 "Routine Vacuuming"
- 실습: 트랜잭션 하나를 열어 둔 채 UPDATE 반복 → 테이블 크기·쿼리 시간 변화 예측 후 측정
- 손으로: 긴 트랜잭션을 찾는 모니터링 쿼리
- 끝: 볼트에 3줄

### DB-05 · 커넥션 풀
- 장면: 트래픽이 조금 늘었는데 응답이 수 초로 / "Connection is not available".
- 이론: 풀 크기는 DB 코어·디스크에 맞춘다(크다고 좋지 않음). 대기 시간 = 풀 고갈. 트랜잭션 안의 느린 일(외부 호출)이 풀을 먹는다.
- 답해 볼 것: ① 풀 10 vs 100에서 처리량은 ② HikariCP 대기 지표 ③ 풀이 고갈될 때 앞단에서 보이는 증상
- 읽을 곳: HikariCP 위키 "About Pool Sizing"
- 실습: 풀 크기 5·10·50·100으로 같은 부하 → 처리량·p99 예측 후 측정
- 손으로: 풀 지표 대시보드에 올릴 3개 고르기
- 끝: 볼트에 3줄

### DB-06 · 페이지네이션과 대량 처리
- 장면: 목록 뒤쪽 페이지가 느림 / 배치가 100만 건을 한 번에 읽다 메모리 부족.
- 이론: OFFSET은 버리는 행도 읽는다 → 키셋(커서) 페이지네이션. 대량 처리는 청크 + 커서 + 커밋 단위.
- 답해 볼 것: ① OFFSET 100만이 느린 이유 ② 키셋에서 정렬 키가 겹치면 ③ 청크 크기를 정하는 기준
- 읽을 곳: use-the-index-luke.com "Paging Through Results"
- 실습: OFFSET vs 키셋을 페이지 1·1,000·10,000에서 측정
- 손으로: 키셋 쿼리
- 끝: 볼트에 3줄
