# OS · 백엔드를 위한 운영체제

> 동시성·네트워크·성능 서가의 공통 바닥.

### OS-01 · 프로세스·스레드·컨텍스트 스위치
- 장면: 스레드를 늘렸더니 오히려 느려짐.
- 이론: 스레드 = 스택 + 커널 스케줄 단위, 컨텍스트 스위치 비용, 실행 큐, CPU 코어 수보다 많은 실행 스레드.
- 답해 볼 것: ① 컨텍스트 스위치가 비싼 이유(캐시) ② CPU 작업 스레드 수의 상한 ③ `vmstat`의 `cs`, `r`
- 읽을 곳: 『운영체제: 아주 쉬운 세 가지 이야기』(OSTEP, 웹 무료) 가상화 편
- 실습: CPU 작업을 스레드 1·코어 수·코어×10으로 → 처리량·cs 예측 후 측정
- 손으로: 결과 표와 해석
- 끝: 볼트에 3줄

### OS-02 · 파일 디스크립터와 소켓
- 장면: "Too many open files"로 서버가 새 연결을 못 받음.
- 이론: 모든 것은 fd(파일·소켓·파이프), 프로세스 한도(`ulimit -n`), 연결 누수, `lsof`.
- 답해 볼 것: ① 연결 1만 개에 fd 몇 개 ② 한도에 걸리면 어디서 실패하나 ③ 누수를 찾는 명령
- 읽을 곳: OSTEP 영속성 편(파일) · `man 2 socket`
- 실습: 연결을 닫지 않는 코드로 fd 한도 재현 → `lsof`로 찾기
- 손으로: 서비스의 fd 한도 설정(systemd `LimitNOFILE`)
- 끝: 볼트에 3줄

### OS-03 · I/O 모델: 블로킹·논블로킹·epoll
- 장면: 연결 1만 개를 스레드 1만 개로 받다 메모리 부족 / Netty·WebFlux는 왜 스레드가 적나.
- 이론: 블로킹 I/O, 논블로킹 + 다중화(select·poll·epoll), 이벤트 루프, 이벤트 루프를 막는 코드의 위험.
- 답해 볼 것: ① epoll이 select보다 나은 이유 ② 이벤트 루프 안에서 DB를 블로킹 호출하면 ③ 가상 스레드와의 관계
- 읽을 곳: "The C10K problem"(Dan Kegel) · `man 7 epoll`
- 실습: 스레드당 연결 서버 vs epoll 서버(Java NIO) — 연결 1만 개 메모리·CPU 예측 후 측정
- 손으로: NIO 셀렉터 루프 50줄
- 끝: 볼트에 3줄

### OS-04 · 메모리: 가상 메모리·페이지 캐시·OOM
- 장면: `free`가 거의 0인데 문제없다고 함 / OOM 킬러가 DB를 죽임.
- 이론: 가상 주소와 페이지, 페이지 캐시는 남는 메모리를 쓴다, 스왑, RSS vs VSZ, OOM 점수.
- 답해 볼 것: ① `free`의 available이 진짜 여유인 이유 ② OOM 킬러가 고르는 기준 ③ 메모리 매핑 파일의 장단점
- 읽을 곳: OSTEP 가상화 편(메모리) · `man 5 proc`(oom_score)
- 실습: 큰 파일을 두 번 읽어 페이지 캐시 효과 측정, 메모리를 채워 OOM 재현(컨테이너에서)
- 손으로: 프로세스 메모리 확인 명령 묶음
- 끝: 볼트에 3줄
