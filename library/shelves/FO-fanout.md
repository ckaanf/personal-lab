# FO · 대규모 실시간 팬아웃

> 스트리밍 플랫폼의 백엔드 쪽 — 채팅·반응·후원이 한 방에 몰릴 때.

### FO-01 · 팬아웃 비용
- 장면: 인기 방송 하나에서 채팅 하나가 10만 명에게 → 서버가 버티지 못함.
- 이론: 메시지 수 × 구독자 수, 쓰기 시점 팬아웃 vs 읽기 시점 팬아웃, 서버 간 브로드캐스트(pub/sub) 비용.
- 답해 볼 것: ① 초당 채팅 100개 × 시청자 10만이면 초당 전송 수 ② 서버가 10대면 pub/sub 메시지는 ③ 인기 방만 다르게 다루는 이유
- 읽을 곳: Twitch Engineering 블로그 채팅 구조 글 · Discord Engineering 글
- 실습: 구독자 1천·1만에서 WebSocket 브로드캐스트 지연·CPU 예측 후 측정
- 손으로: 계산표
- 끝: 볼트에 3줄

### FO-02 · 백프레셔와 느린 소비자
- 장면: 망이 느린 시청자 몇 명 때문에 서버 메모리가 계속 늘어남.
- 이론: 보낼 큐가 쌓임, 느린 연결 끊기·메시지 버리기·합치기, 중요도에 따라 다르게(후원은 꼭, 채팅은 버려도).
- 답해 볼 것: ① 연결마다 큐 상한이 없으면 ② 버려도 되는 메시지와 아닌 것 ③ 합치기(초당 박수 수)의 예
- 읽을 곳: Reactive Streams 명세 개요 · Netty 문서 "Write buffer water marks"
- 실습: 느린 클라이언트 섞기 → 정책별 서버 메모리·다른 사람 지연 측정
- 손으로: 연결별 큐 상한 + 버리기 정책
- 끝: 볼트에 3줄

### FO-03 · 순서와 정합성이 필요한 이벤트 (후원)
- 장면: 후원 알림은 떴는데 결제는 실패 / 같은 후원이 두 번 표시.
- 이론: 화면 이벤트와 돈 이벤트를 나눈다. 돈은 TX 서가(멱등·아웃박스), 화면 알림은 결제 확정 후 at-least-once + 중복 제거.
- 답해 볼 것: ① 알림을 결제 전에 보여 주면 ② 중복 표시를 막는 키 ③ 순서를 지켜야 하는 범위(방 단위)
- 읽을 곳: TX-03·TX-05 카드
- 실습: 결제 확정 → 아웃박스 → 알림 흐름에 장애 주입, 알림 유실·중복 측정
- 손으로: 알림 중복 제거
- 끝: 볼트에 3줄

### FO-04 · 접속 폭주 (썬더링 허드)
- 장면: 방송 시작 알림이 나가자 1분 안에 수십만 명이 동시에 접속.
- 이론: 연결 수립 비용, 재접속 폭주(지터 있는 백오프), 대기열, 정적 자원은 CDN으로, 미리 늘려 두기.
- 답해 볼 것: ① 서버 재시작 후 모두가 동시에 재접속하면 ② 재접속 지터 ③ 대기열을 보여 줄 기준
- 읽을 곳: DS-02 카드 · AWS Builders' Library "Using load shedding to avoid overload"
- 실습: 연결 1만 개를 동시에 vs 지터를 두고 붙여 서버 CPU 피크 비교
- 손으로: 재접속 백오프
- 끝: 볼트에 3줄
