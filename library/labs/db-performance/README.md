# DB 성능 실험실 — 실행 계획 · 인덱스 · 락 · 풀

> 서가: [DB 서가](../../shelves/DB-performance.md). 실습 코드는 `db-lab/performance/`에 둔다.
> 실무에서 "느리다"를 숫자로 설명하고, 고친 뒤 얼마나 나아졌는지 보이는 연습.

## 끝난 기준
1. 질문마다 볼트 `Notes/실험기록/`에 3줄 (`library: DB-0N`).
2. "느린 쿼리 하나를 받으면 하는 순서" 한 장을 내 말로 (볼트).
3. 글 1편: 질문 하나를 골라 전후 숫자와 함께.

## 무대
| 무엇 | 선택 |
|---|---|
| DB | MySQL 8 + PostgreSQL 16 (Docker) — 같은 질문을 두 엔진에서 비교할 때만 둘 다 |
| 데이터 | 주문 1,000만 행 · 회원 100만 행 (생성 스크립트는 AI가, 분포는 내가 정한다: 쏠림 있는 회원, 최근 몰린 날짜) |
| 부하 | k6 (열린 모델) |
| 관측 | `EXPLAIN ANALYZE`, `performance_schema`/`pg_stat_statements`, 슬로 쿼리 로그 |

## 이론 : 실습 = 4 : 6
각 질문은 **이론 30분**(읽을 곳 + 답해 볼 것 3개를 먼저 손으로) → **예측** → **실습** → **설명**.

## 질문
| # | 질문 | 이론 먼저 | 실습 (예측 → 측정) | 손으로 |
|---|---|---|---|---|
| 1 | 이 쿼리는 왜 느린가? | 실행 계획 읽는 순서, 추정 vs 실제 rows | 느린 쿼리 5개의 원인을 계획만 보고 먼저 맞히기 | 계획 해석 메모 |
| 2 | 어떤 인덱스가 맞나? | B-Tree, 왼쪽 접두사, 선택도, 커버링 | 같은 조회에 인덱스 4가지 → 읽은 행·시간, 쓰기 처리량 손해 | 화면 조회 3개용 인덱스 설계 |
| 3 | 통계가 틀리면? | 히스토그램, 상관 컬럼, 쏠린 분포 | 쏠린 회원 조회에서 계획이 바뀌는 지점 찾기 | 통계 갱신 판단 기준 |
| 4 | 뒤쪽 페이지가 왜 느린가? | OFFSET 비용, 키셋 | 페이지 1·1천·10만 시간 표 | 키셋 쿼리 |
| 5 | 동시 갱신에서 락은 어디까지? | 행 락·갭 락, 인덱스 없을 때 범위 | 인덱스 유무로 UPDATE가 막는 범위 재현 | 락 범위 그림 |
| 6 | 데드락은 어떻게 읽나? | 데드락 감지, 락 순서 | 데드락 만들기 → 로그 읽기 → 순서 고정 | 순서 고정 코드 |
| 7 | 긴 트랜잭션이 남에게 주는 피해 | MVCC, 언두·VACUUM | 트랜잭션 하나를 열어 두고 성능 변화 곡선 | 긴 트랜잭션 탐지 쿼리 |
| 8 | 커넥션 풀은 몇 개가 맞나? | 풀 크기 공식, 대기 지표 | 풀 5~100에서 처리량·p99 곡선 | 풀 대시보드 지표 3개 |

## AI에게 맡기는 것 / 내가 하는 것
- AI: 데이터 생성, 컨테이너, k6 스크립트, 측정 결과 표 정리.
- 나: 분포 설계, 인덱스·쿼리, 예측 숫자, 원인 설명. 실행 계획 해석은 AI에게 먼저 묻지 않는다.
