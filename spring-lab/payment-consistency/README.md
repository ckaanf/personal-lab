# 결제 정합성 실험실 — 이중 쓰기 · 멱등성 · 아웃박스

> 강의 없이 하는 학습 패키지 (2026-10-29 시작안). 인프런 "금융 백엔드 실전: Outbox, 멱등성, Dual Write"(Hong)가 다루는 주제를
> **질문 하나 → 예측 → 실험 → 내 말로 설명** 순서로 직접 부딪혀 본다. 정리 노트는 AI가 대신 쓰지 않는다.

## 왜 하나
- 실무 케이스: DB와 외부 시스템(PG·다른 서비스)이 같이 바뀌는 곳은 어디서나 깨진다. "타임아웃 = 실패"가 아니라 "모름"이다.
- AI 활용: 뼈대·장애 주입 서버·부하 스크립트는 AI에게 맡기고, **핵심 로직·예측·판단은 내가** 한다. 검증은 새 세션 리뷰와 불변식 테스트로.

## 끝난 기준 (패키지 전체)
1. 아래 9개 질문마다 `기록.md`에 3줄(예측 / 관찰 / 내 말로 설명)이 있다.
2. 마지막 카오스 테스트가 장애를 무작위로 1,000번 넣어도 불변식 3개를 지킨다.
3. 이 실험을 설명하는 글 1편 (블로그 또는 GitBook).

## 무대
| 무엇 | 선택 | 이유 |
|---|---|---|
| 도메인 | 지갑 충전: 내 잔액 + 외부 PG 승인 | 작지만 이중 쓰기·멱등·동시성·대사가 다 나온다 |
| 서버 | Spring Boot 3 · Java 21 · JPA/JdbcTemplate | 회사 스택과 같다 |
| DB | PostgreSQL 16 (Docker) | 격리 수준·`FOR UPDATE`·유니크 제약 실험 |
| 외부 PG | 가짜 PG (작은 Spring 앱 또는 WireMock) — **지연·타임아웃·500·처리 후 응답 유실·중복 콜백**을 설정으로 켠다 | 장애를 마음대로 만든다 |
| 시험 | JUnit 5 · Testcontainers · 동시 요청은 `ExecutorService` + `CountDownLatch` | 재현 가능하게 |
| 메시지 | 6번까지는 없음. 아웃박스 릴레이는 DB 폴링 → 필요하면 Kafka(Testcontainers) | 처음부터 브로커를 붙이지 않는다 |

**불변식 3개** (모든 실험의 채점 기준)
1. 잔액 = 원장(ledger) 합계
2. 외부 PG가 승인한 건 = 내부에서 성공으로 끝난 건 (대사 뒤)
3. 같은 멱등 키로는 돈이 한 번만 움직인다

## AI와 일하는 규칙 (이 폴더의 CLAUDE.md로 옮겨 둔다)
- 체급 모드: 답을 먼저 주지 않는다. 예측을 먼저 받고, 실험을 같이 만들고, 내 설명에서 틀린 곳만 짚는다.
- AI가 만드는 것: 프로젝트 뼈대, docker-compose, 가짜 PG와 장애 스위치, 부하·동시성 테스트 틀, 대사용 가짜 정산 파일.
- 내가 만드는 것: 상태 설계, 트랜잭션 경계, 멱등 처리, 재시도·보상 정책, 기록 3줄.
- 검증: 구현이 끝나면 **새 세션**에 코드만 주고 "어디서 돈이 두 번 움직일 수 있나"를 묻는다 (자기 선호 편향 피하기).

## 커리큘럼 (질문 하나 = 한 번 앉아서 1~2시간)
| # | 질문 | 실험 | 핵심 개념 | 끝난 기준 |
|---|---|---|---|---|
| 0 | 무대가 서나? | compose로 Postgres + 가짜 PG 띄우고 충전 API 한 번 성공 | — | `POST /charge` 200, 잔액·원장 1줄 |
| 1 | DB 커밋 → PG 호출 순서와 그 반대, 어디서 깨지나? | 두 순서 × 실패 지점(호출 전·중·후·커밋 실패) 표를 **먼저 예측**하고 장애 스위치로 채운다 | 트랜잭션이 지키는 범위, 이중 쓰기 | 8칸 표: 예측 vs 실제 |
| 2 | 타임아웃이 나면 결제됐나? | PG가 처리 후 응답을 버리게 한다 → 내부는 실패, PG는 승인 | "모름" 상태, 조회 API로 확정, exactly-once는 없다 | `UNKNOWN` 상태 + 확정 잡으로 불변식 2 회복 |
| 3 | 사용자가 두 번 누르면? | 같은 요청 2개를 동시에(래치) · 순차로 · 첫 요청 처리 중에 | 멱등 키 테이블, 유니크 제약, 저장된 응답 재생, 처리 중 상태 | 동시 100번에도 돈 한 번 (불변식 3) |
| 4 | 잔액 차감이 동시에 들어오면? | 충전·사용 동시 1,000건: 그냥 UPDATE / `SELECT … FOR UPDATE` / 조건부 `UPDATE … WHERE balance >= ?` / `@Version` | 격리 수준(READ COMMITTED vs REPEATABLE READ), lost update, 락 대기 시간 | 방식별 정합성·처리량 표 |
| 5 | 상태가 꼬이면? | 콜백이 요청보다 먼저 오기, 성공 뒤 실패 콜백, 같은 콜백 3번 | 상태 머신, 허용 전이 표, 전이 이력 | 허용 안 된 전이는 모두 거절되고 이력에 남는다 |
| 6 | "충전 완료" 알림이 빠지거나 두 번 가면? | DB 커밋 뒤 이벤트 발행 실패 → 아웃박스 테이블 + 폴링 릴레이 → 릴레이 중복 실행 | 트랜잭셔널 아웃박스, at-least-once, 소비자 멱등 | 릴레이를 죽였다 살려도 이벤트 유실 0, 중복은 소비자가 흡수 |
| 7 | 계속 실패하면 언제 멈추나? | PG 500 연속 · 간헐 실패 | 재시도(백오프·최대 횟수), 보상(환불) vs 보류(수동 확인 큐), 요청 테이블과 작업 테이블 분리 | 정책 표 + 보류 큐에 쌓인 건을 사람이 처리하는 흐름 |
| 8 | 하루 끝에 맞는지 어떻게 아나? | 가짜 정산 파일(누락·중복·금액 차이 섞음) ↔ 내부 원장 | 대사(reconciliation) 쿼리, 차이 리포트 | 세 종류 차이를 모두 찾아내는 쿼리 |
| 9 | 다 섞으면 버티나? | 장애를 무작위로 1,000번 (시드 고정) | 카오스 테스트, 불변식 검사 | 불변식 3개 통과 + 실패 시 재현 시드 |
